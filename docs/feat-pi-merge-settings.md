# Feature: Merge Pi Settings at Container Entrypoint

## Problem

The sandbox contract is:

- Binaries and extensions are installed at **docker build time** and baked into the image.
- User data lives in the host's `${DATA_DIR}` directory, which is bind-mounted to `/home/user` at runtime.

Pi breaks this contract because `pi install <extension>` writes extension records into the user's `settings.json` (in their HOME). When extensions are installed during `docker build` (via `POST_INSTALL_SCRIPT`), they are written to the `node` user's home inside the image (`/home/node/…`). At runtime, HOME is overridden to `/home/user` (the bind-mount), so those extension entries are silently absent—even though the extension code was installed into the image.

## Goal

Restore the contract: extensions declared in the image stay active at runtime regardless of the user's own settings, while the user's personal settings are preserved and take precedence for any conflicts.

## Solution Overview

1. **During build**: run `pi install` as normal; copy the resulting settings file out of the build-time HOME to a stable, world-readable path inside the image (e.g. `/usr/local/share/pi/build-settings.json`).
2. **At runtime**: a custom entrypoint script runs before `pi` and merges the build-time settings into the user's live settings file, then hands off to the original command.

---

## Implementation Plan

### Step 1 — Identify Pi's Settings Path

Before writing any code, confirm where `pi install` actually writes its settings. The most likely candidates are:

- `~/.pi/settings.json`
- `~/.config/pi/settings.json`

Run `pi install npm:pi-tasks` inside a throw-away container and inspect both paths:

```bash
docker run --rm -it --entrypoint bash \
  $(docker compose -f internal/compose/compose.yaml images -q pi) \
  -c "pi install npm:pi-tasks && find /home/node -name 'settings.json' 2>/dev/null"
```

Use whatever path is confirmed as `SETTINGS_PATH` in the steps below. The plan assumes `~/.config/pi/settings.json`; adjust if different.

---

### Step 2 — Dockerfile Changes (`internal/compose/nodejs.Dockerfile`)

After the existing `POST_INSTALL_SCRIPT` step, add a `RUN` layer that copies the build-time settings to a stable system path and makes the entrypoint script available:

```dockerfile
ARG POST_INSTALL_SCRIPT
RUN if [ -n "${POST_INSTALL_SCRIPT}" ]; then sh -c "${POST_INSTALL_SCRIPT}"; fi

# Preserve settings generated by POST_INSTALL_SCRIPT for runtime merging.
# The destination path must not be inside HOME so it survives the bind-mount.
RUN mkdir -p /usr/local/share/pi && \
    if [ -f /home/node/.config/pi/settings.json ]; then \
      cp /home/node/.config/pi/settings.json /usr/local/share/pi/build-settings.json && \
      chmod 644 /usr/local/share/pi/build-settings.json; \
    fi
```

Also copy the entrypoint script (created in Step 3) into the image:

```dockerfile
COPY pi-entrypoint.sh /usr/local/bin/pi-entrypoint.sh
RUN chmod +x /usr/local/bin/pi-entrypoint.sh
```

The `COPY` instruction requires the file to be in the build context (`internal/compose/`), so place `pi-entrypoint.sh` there.

---

### Step 3 — Entrypoint Script (`internal/compose/pi-entrypoint.sh`)

This script runs at container start, merges settings, then delegates to the normal `bash -c` flow that `launch.sh` relies on.

```bash
#!/bin/bash
# Merge build-time pi extension settings into the user's live settings.json.

BUILD_SETTINGS="/usr/local/share/pi/build-settings.json"
USER_SETTINGS="${HOME}/.config/pi/settings.json"  # adjust if Step 1 reveals a different path

if [ -f "${BUILD_SETTINGS}" ]; then
  if [ -f "${USER_SETTINGS}" ]; then
    # Merge strategy:
    #   - User settings are the base (their values win on conflicts).
    #   - Build-time extensions are unioned into the user's extension list.
    #     unique_by(.name) deduplicates if the user already has the same extension.
    MERGED=$(jq -s '
      .[0] as $build |
      .[1] as $user |
      $user | .extensions = (
        (($build.extensions // []) + ($user.extensions // []))
        | unique_by(.name // .)
      )
    ' "${BUILD_SETTINGS}" "${USER_SETTINGS}")
    echo "${MERGED}" > "${USER_SETTINGS}"
  else
    mkdir -p "$(dirname "${USER_SETTINGS}")"
    cp "${BUILD_SETTINGS}" "${USER_SETTINGS}"
  fi
fi

# Hand off to the normal entrypoint flow (bash -c "<cmd>" -- <args...>).
exec bash -c "$@"
```

`jq` is already installed in the image, so no new dependencies are needed.

**Merge semantics:**

| Key | Winner |
|---|---|
| Scalar/object fields other than `extensions` | User settings |
| `extensions` array | Union; build-time entries are prepended, deduped by `.name` |

If pi's settings schema is more complex (e.g. extensions are objects with a different unique key), adjust the `unique_by` predicate accordingly.

---

### Step 4 — compose.yaml Changes

Uncomment the `POST_INSTALL_SCRIPT` for pi and override its entrypoint to use the new script:

```yaml
pi:
  <<: *cli_tool
  build:
    context: .
    dockerfile: nodejs.Dockerfile
    args:
      NPM_PACKAGE: "@mariozechner/pi-coding-agent"
      POST_INSTALL_SCRIPT: |-
        pi install npm:pi-tasks
        pi install npm:pi-ask-user
  entrypoint: ["/usr/local/bin/pi-entrypoint.sh"]
```

The parent `*cli_tool` anchor sets `entrypoint: ["bash", "-c"]`; this override replaces it only for pi. `launch.sh` passes the command as `"pi \"$@\"" -- <args>`, so the entrypoint receives that string as `$1` and the user's arguments after `--`. The final `exec bash -c "$@"` in the entrypoint script reconstructs the original invocation correctly.

---

### Step 5 — Rebuild and Test

```bash
# Full rebuild to pick up Dockerfile changes
pi :rebuild

# Verify the build-time settings were captured in the image
docker run --rm \
  $(docker compose -f internal/compose/compose.yaml images -q pi) \
  cat /usr/local/share/pi/build-settings.json

# Smoke test: run pi normally and confirm extensions are active
pi --help
```

Also test the idempotency case: run pi twice with an already-populated `${DATA_DIR}` and confirm the merge does not duplicate extensions.
